Overview

Wowser uses a centralized state management pattern built around DataStore<Model>, a generic class that wraps an immutable, Codable value type and provides:

  • Thread-safe access via a dedicated queue
  • Reactive updates via Combine publishers
  • Automatic persistence to JSON files
  • Frame-throttled UI updates for smooth rendering

Core Architecture

DataStore.swift

The base class that manages state:

open class DataStore<Model: Equatable & Codable>: NSObject {
    private var _model: Model           // The actual state
    private var subject: CurrentValueSubject<Model, Never>

    public let persistenceKey: String?  // Key for JSON file
    public let queue: Queue              // Thread synchronization

    // Two publishers for different use cases
    public var publisher: AnyPublisher<Model, Never>    // Immediate
    public var uiPublisher: AnyPublisher<Model, Never>  // Frame-throttled
}

BrowserStore Example

The main application state store:

public class BrowserStore: DataStore<BrowserState> {
    public static let shared = BrowserStore(
        persistenceKey: "BrowserStore",
        defaultModel: .defaultState,
        queue: .main
    )

    private var liveWebContents = [ID<WebContent>: WebContent]()
}

Observing State

There are three main patterns for observing DataStore changes:

1. WithSnapshotMain (Recommended for UI)

Creates an efficient, equatable snapshot of only the data your view needs. Re-renders only when the snapshot changes. 

struct DownloadsSidebar: View {
    let windowID: ID<WindowState>

    var body: some View {
        WithSnapshotMain(store: BrowserStore.shared) { state in
            // Create minimal snapshot with only needed data
            DownloadsSnapshot(
                windowID: windowID,
                downloads: state.windows[windowID]?.downloads ?? [:]
            )
        } main: { snapshot in
            // Render view with snapshot (non-optional)
            DownloadsSidebarContent(snapshot: snapshot)
        }
    }
}

// Define an Equatable snapshot struct
private struct DownloadsSnapshot: Equatable {
    let windowID: ID<WindowState>
    let downloads: [ID<Download>: Download]
}

2. onReceive with uiPublisher

Direct Combine subscription for simpler cases or when you need to trigger side effects. 

struct MyView: View {
    @State private var shouldFocus = false
    let windowID: ID<WindowState>

    var body: some View {
        Color.clear
            .onReceive(
                BrowserStore.shared.uiPublisher
                    .map { $0.shouldFocusWebContent(windowID) }
                    .removeDuplicates()
            ) { shouldFocus in
                self.shouldFocus = shouldFocus
            }
    }
}

3. WithSnapshot (for async/background stores)

Similar to WithSnapshotMain but returns an optional snapshot, suitable for stores that may not have loaded yet. 

WithSnapshot(store: someBackgroundStore) { state in
    MySnapshot(data: state.relevantData)
} main: { snapshot in  // snapshot is optional
    if let snapshot {
        ContentView(snapshot: snapshot)
    } else {
        LoadingView()
    }
}
Pattern Use When Snapshot
WithSnapshotMain Main-thread stores (BrowserStore) Non-optional
WithSnapshot Background stores, async loading Optional
onReceive Simple values, side effects N/A
Tip: Always use uiPublisher for UI updates, not publisher. The uiPublisher is throttled to the display refresh rate (60fps), preventing excessive redraws during rapid state changes.

Modifying State

modify() - Synchronous Modification

The primary way to update state. Runs on the store's queue.

BrowserStore.shared.modify { state in
    // Mutate state directly
    state.windows[windowID]?.currentTab = tabID

    // Call extension methods
    state.openTab(url: url, activate: true)
}

modifyAsync() - Async/Await Modification

For use in async contexts. Returns a value if needed.

func updateTabs() async {
    await BrowserStore.shared.modifyAsync { state in
        state.tabs[tabID]?.aiTags = newTags
    }
}

// Can also return values
let tabCount = await store.modifyAsync { state in
    state.tabs.count
}

readAsync() - Async Reading

Read state without modification in async contexts.

let currentState = await store.readAsync()

// Or with a transform
let tabIDs = await store.readAsync { state in
    Array(state.tabs.keys)
}
Warning: Never call modify() from within another modify() block. The store has an assertion to catch this. Instead, perform all mutations in a single modify call.

Persistence

DataStore automatically persists to JSON files in Application Support:

~/Library/Application Support/WowserDataStores/{BundleID}/{persistenceKey}.json

Automatic Save Triggers

  • App resigns active (goes to background)
  • App terminates

Lifecycle Hooks

class MyStore: DataStore<MyState> {
    // Called during initialization
    override func setup() {
        super.setup()
        // Setup subscriptions, background tasks, etc.
    }

    // Called after loading from disk
    override func processModelAfterLoad(model: inout MyState) {
        model.cleanupStaleData()
    }

    // Called before saving to disk
    override func processModelBeforePersist(model: inout MyState) {
        model.removeTransientData()
    }

    // Called periodically before saves
    override func cleanup(model: inout MyState) {
        model.trimOldEntries()
    }

    // Migration from old data formats
    override func migrate(previousData: Data) -> MyState? {
        // Try to decode old format and convert
        return nil
    }
}

Concurrency

The Queue System

Each DataStore has an associated Queue that manages thread safety:

public struct Queue {
    public let id: String
    public let queue: DispatchQueue

    public static let main = Queue(id: "main", queue: .main)

    // Runs async if not current, sync if already on queue
    public func run(_ block: @escaping () -> ()) { ... }

    // Always runs sync (warns if blocking main)
    public func runSync(_ block: () -> ()) { ... }
}

Store Queue Patterns

Store Queue Reason
BrowserStore .main UI state, needs immediate sync access
HistoryStore .historyQueue Background data, avoids blocking UI
ArchiveStore Custom Background processing

FrameThrottledValue

The uiPublisher uses a display-link-based throttling mechanism to coalesce rapid updates into single frames: 

class FrameThrottledValue<V> {
    private var pendingVal: V?
    private var displayLink: DisplayLink?

    func update(value: V) {
        // Store pending value
        pendingVal = value

        // Create display link if needed
        if displayLink == nil {
            displayLink = DisplayLink { [weak self] in
                // Publish on next frame, then clean up
                self?.subject.value = self?.pendingVal
                self?.displayLink?.invalidate()
            }
        }
    }
}
Multiple rapid updates: t=0ms: modify() ──▶ pendingVal = A t=1ms: modify() ──▶ pendingVal = B t=2ms: modify() ──▶ pendingVal = C t=16ms: DisplayLink fires ──▶ publish(C) ──▶ UI renders once

Best Practices Summary

Do:
  • Use WithSnapshotMain with minimal, equatable snapshots
  • Put business logic in extensions on the state type
  • Use uiPublisher for UI subscriptions
  • Extend BrowserState rather than BrowserStore when possible
  • Keep state types JSON-serializable
Don't:
  • Nest modify() calls
  • Store large data (images, callbacks) in state
  • Use publisher for UI (use uiPublisher)
  • Block the main thread with runSync from background queues
